# CTBP5001 GIR Extraction — Test Data Preparation Guide

Source: `ref/5001.xlsx` (126-scenario test matrix for CTBP5001 — GIR extraction & XML generation, HK → partner jurisdictions, OECD Pillar Two)

Schema reference: `ref/GLOBEXML_v1.0.xsd` (OECD GIR v1.0 — the contract for the generated XML; the file is then encrypted as `.dat` for P2P upload)

OECD guideline PDFs in `ref/`:

- `GloBE Information Return (Pillar Two) XML Schema.pdf` (Jan 2025, 171 pp) — official OECD User Guide for the GIR XML Schema; source of the business rules in §11
- `GloBE Information Return (Pillar Two) Status Message XML Schema.pdf` (2025, 70 pp) — User Guide for the GIR Status Message schema + file/record error codes (50001+, 60001+); governs CTBP5011/CTBP5004 expectations
- `oecd-classification-taxes-interpretative-guide.pdf` (Revenue Statistics 2023, Annex A) — general OECD tax-classification background (1000–6000 headings); no direct CTBP5001 test impact

Coverage: extraction filters, jurisdiction partner windows, grouping (TIN × jurisdiction × year), GIR101/GIR102 file generation, 30,000-record split rules, DocRefId construction, XML escaping, GIR_CNT/AMEND_CNT counting rules, and the downstream approval/sign/transmit lifecycle.

---

## Design Principles

1. **Use a distinct key combination (FCE_TIN × REC_JDX_CTRY × RPT_YR) per scenario family** so branches don't interfere within one auto-mode run.
2. **Use isolated runs with a reset DB** for boundary/mode tests (30,000 split, empty DB, invalid parameter).
3. **Fix the run date = 2026-07-20** so DocRefId assertions are deterministic (e.g. `HK2025IDT123-20260720-0001`).

## 7. Special-Character Content (one TIN, e.g. T999/ID/2025)

Entity/section text values:

- `A&B`, `A<B`, `A>B`, `O'Brien`, `Say "Hi"` → verify `&amp; &lt; &gt; &apos; &quot;`
- `A--B`, `A/*B`, `A&#B` → rejected (no `--`, `/*`, `&#` in output)
- A value where escaping itself would create `&#` (e.g. `&` followed by `#`) → escaping order must not re-introduce it

## 9. Run Variants & Lifecycle Sequencing

Run variants:

- Auto mode (no parameter) on the full seeded DB
- Ad-hoc `ID 2025` (valid format `XX 9999`)
- `ID2025` (invalid — confirm behaviour)
- `IE 2025` while IE is in Phase B/C state (IS_PARTNER='N') → no records extracted

1. After CTBP5001 assert `APRVD_STS='P'`
2. CTAP5002 approve → `A` / `SGD_STS='P'` (reject path on a second run → `R`, SGD_STS NULL)
3. CTBP5002 sign/encrypt → `S`, CTS_TX_REC.TX_STS='R', TRANSMISSION_FLAG='Y'

5. CTBP5004 status message → TRANSMISSION_FLAG=NULL, DOC_REF cleared
6. File placement: assert `\data\out\pending\<MessageRefId>.xml` and `.metadata.xml`

## 10. Evidence Capture — When to Record DB Data / XML Before & After

Baseline rule: **every step that mutates data or produces files needs a BEFORE and AFTER snapshot.** Most assertions in the matrix are either absence-based ("record not extracted") or counter/status-based (GIR_CNT, APRVD_STS), which are unprovable without a prior snapshot.

Key tables to snapshot: GIR source records, `GIR_MSG_SPEC`, `FILING_INFO`, `GEN_SEC`, `JDX_SEC`, `SMRY`, `UTPR_ATTR`, `CTS_TX_REC`, Jurisdiction Table (for IE phases A–D), plus the `\data\out\pending\` folder listing.

| Step | Record BEFORE | Record AFTER |
|---|---|---|
| Jurisdiction reconfig (IE Phase A/B/C/D) | Jurisdiction Table row for IE | New IE row — proves which phase config the run saw |
| CTBP5001 run (each variant) | Full DB snapshot + counts of all GIR_* tables + `GIR_MSG_SPEC` (GIR_CNT/AMEND_CNT should be 0/NULL) | Same tables + copies of every generated `*.xml` and `*.metadata.xml` + MessageRefId list |
| Exclusion tests (status/flags/already-sent/window/non-partner/absent JDX) | The candidate GIR records with their qualifying attributes | Same records — prove they exist BEFORE but are absent from V_EXT output / generated XML |
| Grouping / multi-file runs | List of key combos (TIN × JDX × YR) seeded | File inventory: one MessageRefId per combo, sequence numbers |
| Split runs (V1/V2/V2b/V3) | Total seeded element count | Every file + per-file element count (assert each ≤ 30,000; V3 = 30k/30k/5k) |
| Counting matrix (§8) | `GIR_MSG_SPEC.GIR_CNT` / `AMEND_CNT` per MessageRefId | Updated values via UPDATE_TX_CNT; diff against expected +1/+0 |
| Audit-column checks | DB session timestamp / RUN_BY user | LAST_UPD_AT / CREATED_AT / CREATED_BY / LAST_UPD_BY on the six tables |
| CTAP5002 approve / reject | `GIR_MSG_SPEC` (APRVD_STS, SGD_STS) | APRVD_STS='A'+SGD_STS='P' / 'R'+NULL |
| CTBP5002 sign & encrypt | `GIR_MSG_SPEC`, `CTS_TX_REC` | SGD_STS='S', TX_STS='R', TRANSMISSION_FLAG='Y' |
| CTBP5011 status update | `CTS_TX_REC.TX_STS` | New TX_STS (T/N/U/F) |
| CTBP5004 status message received | TRANSMISSION_FLAG + DOC_REF flags | TRANSMISSION_FLAG=NULL, DOC_REF cleared — proves extraction re-enabled |

Practical tips:

- Archive generated XML **immediately after the run** — downstream CTBP5002/5011 may move or consume files from `\data\out\pending\`.
- Snapshot with `ORDER BY` on primary keys so before/after diffs cleanly; keep one evidence folder per run variant / IE phase.
- For absence assertions, the BEFORE snapshot is mandatory — it is the only way to distinguish "correctly excluded" from "never existed".

## 11. XML Schema Constraints (GLOBEXML_v1.0.xsd) for Seed Data & Validation

`ref/GLOBEXML_v1.0.xsd` (OECD GIR v1.0, namespace `urn:oecd:ties:globe:v2`) defines the contract for the generated file — the XML is later encrypted as `.dat` for P2P upload. The official OECD User Guide (`GloBE Information Return (Pillar Two) XML Schema.pdf`) adds business rules the XSD alone does not encode. Seed data and output assertions must respect both so the schema-validation scenario passes.

### Message structure

| Level | Schema rule | Test impact |
|---|---|---|
| Root | `GLOBE_OECD` (optional `version` attribute, ≤10 chars) → `MessageSpec` + `GLOBEBody` (1..unbounded) | One file may hold many GLOBEBodies — counting-matrix row 10 ("one MessageSpec, 3 FilingInfo") = 3 `GLOBEBody` elements under one `MessageSpec` |
| MessageSpec | strict `xsd:sequence`: SendingEntityIN? → TransmittingCountry → ReceivingCountry → MessageType → Warning? → Contact? → MessageRefId → MessageTypeIndic → ReportingPeriod → Timestamp | Element order in the output XML is fixed; out-of-order generation is a schema failure even when all values are correct |
| GLOBEBody | `FilingInfo` (exactly 1, with DocSpec) then **in order**: GeneralSection (0..1), Summary (0..n), JurisdictionSection (0..n), UTPRAttribution (0..n) — each with its own DocSpec | FilingInfo-only GLOBEBody is schema-valid → confirms the "filing-entity-correction file, no sections" scenario; per-section DocSpec is where GIR102 carries OECD2/OECD3 DocTypeIndic and `-S-`/`-U-` DocRefId + CorrDocRefId |

### Schema facts the seed data must respect

1. **MessageSpec has no DocRefId element.** The matrix's "MessageSpec DocRefId" expectation (`HK2025IDT123-20260720-0001`) maps to **MessageRefId** (1–170 chars). DocRefId exists only inside each section's `stf:DocSpec`.
2. **MessageType is the fixed enum value `GIR`** (the message family) — distinct from MessageTypeIndic (GIR101/102/103).
3. **MessageTypeIndic enum: `GIR101` (new) / `GIR102` (correction) / `GIR103` (no data to report).** GIR103 is never exercised in the 126-scenario matrix — confirm with the business whether an empty-DB run should emit a GIR103 nil message or no file at all (current expectation: no file).
4. **FilingCE Role enum**: GIR401=Ultimate Parent Entity, GIR402=Designated Filing Entity, GIR403=Designated Local Entity, GIR404=Constituent Entity, GIR405=Other. The T225 "filed by neither UPE nor DFE" negative test should seed Role = GIR403/GIR404/GIR405.
5. **All monetary amounts are `xsd:integer`** — whole numbers only; no decimals in seeded amounts.
6. **`percentage` = decimal 0–1 with ≤4 fraction digits** — 25% must be seeded and asserted as `0.2500`, never `25`. Applies to ownership %, ETR rates, UTPR percentage, SBIE mark-ups, inclusion ratios.
7. **Dates are `xsd:date` (`YYYY-MM-DD`); Timestamp is `xsd:dateTime`** — RPT_YR=2025 → ReportingPeriod `2025-12-31`.
8. **String length limits apply AFTER XML escaping**: Name/FAS/SendingEntityIN ≤200, MessageRefId/Description ≤170, Warning/Contact/AdditionalInfo/Text ≤4000. T999 values expand when escaped (`&`→`&amp;` = 5 chars, `<`→`&lt;`, `'`→`&apos;`, `"`→`&quot;`) — keep raw values short enough that the escaped form still fits the limit.
9. **TIN element attributes**: optional `issuedBy` (ISO country), `unknown` (boolean), `TypeOfTIN` (GIR3001 TIN / GIR3002 functionally equivalent number / GIR3003 agreed GIR designated number / GIR3004 not required) — seed at least one TIN per type across the matrix.
10. **Country and currency codes are ISO-typed** (`iso:CountryCode_Type`, `iso:currCode_Type`) — only valid ISO 3166 / ISO 4217 values (ID, CA, IE for countries; a valid currency code for AccountingInfo).

### Missing schema dependencies (blocker for machine validation only)

`GLOBEXML_v1.0.xsd` imports two schemas that are **not present in `ref/`**:

- `isoglobetypes_v1.1.xsd` — CountryCode_Type, currCode_Type
- `oecdglobetypes_v5.0.xsd` — the `stf:` namespace: DocSpec_Type, the StringMin1Max… base types, and the DocTypeIndic enumeration

The status-message schema likewise needs `GIRStatusMessageXML_v1.0.xsd` + `isocsmtypes_v1.1.xsd`.

The OECD User Guide PDF documents the DocTypeIndic values in full (below), so **seed data is not blocked** — only standalone XSD validation is. Fetch the XSDs before the schema-validation scenario.

### DocTypeIndic — full enumeration and usage rules (OECD User Guide, Corrections chapter)

| Code | Meaning |
|---|---|
| OECD0 | Resent Data |
| OECD1 | New Data |
| OECD2 | Corrected Data |
| OECD3 | Deletion of Data |
| OECD10 | Resent Test Data |
| OECD11 | New Test Data |
| OECD12 | Corrected Test Data |
| OECD13 | Deletion of Test Data |

Rules:

- A message contains new records (OECD1) **or** corrections/deletions (OECD2/OECD3) — never a mixture.
- **OECD0 (resend) may be used only on the FilingInfo element**, when that FilingInfo has already been sent — this is exactly the split-file rule (1st file FilingInfo=OECD1, subsequent files OECD0).
- OECD10–13 are for agreed testing periods / bilateral agreement only. Receivers **reject live files containing OECD10–13 (error 50009)** and **reject test-environment files containing OECD0–3 (error 50008)**. Confirm which range CTBP5001 emits in this environment — the counting matrix (§8) mixes OECD_1/OECD_0/OECD_2 with OECD_11, so the receiving link must be a CTS test link if OECD10–13 appear.

### Corrections semantics the receiver enforces (record errors 60001+)

GIR102 seed data (§4) must satisfy:

- **DocRefID** format `[SendingCC][Year][UniqueID]`, ≤200 chars, **unique in space and time** (60001/60007/60011); a corrected/deleted record gets a **new** DocRefID.
- **CorrDocRefID** must reference the **latest** DocRefID sent for that record (60009), concern the **same sub-section kind** as the correcting record (60005), be unique within the message — no correcting the same DocRefID twice in one file (60006) — and be **omitted when DocTypeIndic is OECD1/OECD0** (60012).
- **OECD0 is invalid on section-level DocSpecs** — only FilingInfo may carry it (60013).
- **Deleting FilingInfo requires deleting all its sections** (GeneralSection/Summary/JurisdictionSection/UTPRAttribution — 60010); whole-message cancellation = a correction message deleting every record (there is no message-level cancel element).
- Correction messages need their **own new unique MessageRefID** (they may themselves be corrected later).
- MessageRefID format `[SendingCC][Year][ReceivingCC][UniqueID]`, ≤170 chars (60001); duplicates across files rejected (60002); ReportingPeriod year ≤ current year (60003).

### Data conventions from the User Guide

- Booleans: only `true`/`1` and `false`/`0`.
- Amounts: round decimals to the nearest whole number for GIR reporting (xsd:integer).
- Election/revocation years: enter as the **first day of the year**, e.g. `2027-01-01`.
- Percentage: 0–1, up to 4 decimals, max 6 characters.
- ResCountryCode: ISO 3166-1 **plus the X5 code for Stateless Constituent Entities** (pairs with subgroup type GIR1106).
- Receiver-side calculation validations round to 4 decimals and tolerate a **1% margin** before reporting an error.

### Transmission pipeline (CTBP5002 → P2P .dat upload)

The status-message file errors (50001–50011) reveal what the receiving side does — mirror this in CTBP5002/CTBP5011 tests:

**download → decrypt (50002) → decompress (50003) → verify digital signature (50004) → security scan (50005/50006) → XML schema validation (50007) → record validations (60001+)**

- Compression happens **before** encryption (error 50003 says "compress the file (before encrypting)").
- Encryption specifics enforced by 50011: **AES in CBC mode** (not ECB or others), key file contains the IV, combined IV+AES data-packet key must be **48 bytes** (32-byte key + 16-byte IV, concatenated).
- Security scan rejects hyperlinks, JavaScript, executables and viruses — **plain-text URLs are allowed**.
- 50010: a file whose records aren't meant for the receiver (ReceivingCountry mismatch) must be deleted by the erroneous receiver and reported back.

### GIR Status Message expectations (CTBP5011 / CTBP5004)

- One status message per GIR file, tied via `OriginalMessageRefID`; **no status messages about status messages**.
- Status = **Accepted** or **Rejected**. Rejection requires at least one error; **severe record errors ⇒ reject the whole file**; other record errors ⇒ generally **accepted with errors**; minor XML validation issues may still be accepted.
- After a Rejection: fix and resend with a **new MessageRefID** (traceability); a correction message is not needed because the rejected file is ignored — unless the rejected file was itself a correction, in which case the resend keeps the same type.
- **15-day rule**: do not send corrections/deletions of a file until the earlier of an Accepted status or 15 days after sending.
- Status-message MessageRefID convention: starts with the word `Status`, then the original receiver's country code, the year, the original sender's country code, then a unique id — e.g. `StatusFR2027CA123456789`.
- Record errors identify the offending record via `DocRefIDInError` (repeatable) and `FieldPath` (XPATH without namespaces).
- Map the internal TX_STS values (T/N/U/F, §9 step 4) and CTBP5004's TRANSMISSION_FLAG/DOC_REF clearing against these Accepted/Rejected + error-code outcomes.

## Watch-Outs

- **Environment constraint — JDX limited to ID, CA, IE**: all negative jurisdiction scenarios (future start, past cessation, absent from table, non-partner) are produced by reconfiguring IE's effective dates / removing its row in isolated phases. Never point these tests at ID or CA — they must remain in-window partners for every other scenario.
- **Spelling duality**: DB stores `OECD_1`/`GIR_101` (underscored) but XML emits `OECD1`/`GIR101` — seed data with the underscored form and assert the emitted form.
- **ReportingPeriod**: RPT_YR=2025 must emit `2025-12-31`.
- **Audit columns**: capture DB session timestamp to verify LAST_UPD_AT/CREATED_AT; use a dedicated RUN_BY user for CREATED_BY/LAST_UPD_BY assertions.
- Reset or archive GIR_MSG_SPEC / FILING_INFO / GEN_SEC / JDX_SEC / SMRY / UTPR_ATTR between runs so "already sent" and OECD1-vs-OECD0 tests don't contaminate each other.
- **Snapshot discipline**: take the BEFORE DB snapshot before starting each run, not after seeing the result — retroactive "before" captures invalidate absence-based evidence (see §10).
- **Record XML evidence per file, not per run**: MessageRefId, sequence number, FilingInfo DocTypeIndic (OECD1/OECD0) and DocRefId pattern must be captured for each split file individually.
- **Schema validation needs the imported XSDs**: `isoglobetypes_v1.1.xsd` and `oecdglobetypes_v5.0.xsd` (GIR), plus `GIRStatusMessageXML_v1.0.xsd` and `isocsmtypes_v1.1.xsd` (status message), are referenced but absent from `ref/` — fetch them before the schema-validation scenario (§11). DocTypeIndic values are documented in the OECD User Guide PDF, so seed data isn't blocked — only machine validation is.
- **Test vs live DocTypeIndic**: OECD10–13 mark test data — a CTS test link rejects OECD0–3 (error 50008), a live link rejects OECD10–13 (50009). Confirm which range this environment expects before asserting DocTypeIndic values (§8, §11).
- **Percentages are 0–1 decimals (≤4 dp) and amounts are plain integers** — seed and assert `0.1500` and `1234567`, not `15` / `12345.67` (§11).
- **Escaping expands strings** — special-character test values must still fit Max200/Max4000/Max170 after `&amp;`-style escaping (§7, §11).
